# Multiplayer Baseline

This document defines the multiplayer constraints that the Kristal implementation must preserve.
It is an architecture baseline, not a claim that Kristal currently has networking support.

## Product rules

- Single-player remains a first-class mode and must work with networking unavailable.
- Multiplayer must not change the encounter's established story, party roles, turn rules, or
  solo balance by silently changing game rules.
- A session has one host and one or more clients. The host owns the authoritative game state.
- Clients send player intents (menu choice, target, movement/input state); clients do not submit
  authoritative damage, HP, TP, status, phase, or reward values.
- The host validates every intent against the current phase, actor, target, costs, and turn state.
- All participants receive the same ordered result events and state revisions.

## Authority and synchronization

- The host is authoritative for battle state, encounter progression, RNG, enemy scheduling,
  damage resolution, item counts, TP, status effects, and victory/defeat.
- Random outcomes are generated by the host. A session seed and monotonically increasing event
  sequence make desyncs diagnosable and replays reproducible.
- State snapshots are the recovery mechanism; ordered events are the normal update mechanism.
- Every command includes a session ID, sender/player ID, command ID, and the state revision it
  was based on. Duplicate command IDs are ignored.
- A stale or illegal command is rejected with a reason and the latest state revision; it is never
  applied optimistically as authoritative state.
- The host periodically emits a compact snapshot and emits a full snapshot after reconnect.
- The host validates protocol version, game version, content/build hash, and feature capabilities
  before a client joins. Incompatible builds do not enter a session.

## Turn ownership

- A battle turn has one authoritative phase and a clear action owner.
- Simultaneous choices are collected as intents, then resolved in a stable order by the host.
- The host controls enemy turns and all enemy attack scheduling.
- Disconnects do not silently consume another player's turn. The host pauses at a safe decision
  boundary or applies a clearly surfaced session policy.
- Reconnect restores the latest snapshot and then replays later ordered events.
- Pause, surrender, host migration, and drop-in/drop-out rules remain explicit future decisions;
  none should be inferred by the transport layer.

## Transport boundary

- Gameplay code depends on a small session interface, not a specific networking library.
- The interface needs: create/join/leave session, send command, receive event, request snapshot,
  report connection state, and close session.
- Transport selection is intentionally open. Do not couple combat rules to a particular relay,
  lobby provider, socket API, or platform account system before that choice is made.
- Local single-player uses the same command validation and state transition path without a
  network transport. This keeps solo and multiplayer rules aligned.

## Kristal integration constraints

- Kristal's standard battle loop remains the runtime owner until a separate integration proves
  otherwise; networking must not replace or fork the engine loop casually.
- The combat state module should remain the rules layer. A future adapter translates validated host
  commands into calls on that state and emits resulting events.
- UI, encounter, enemy, and wave scripts render replicated state; they do not independently
  calculate authoritative outcomes.
- SOUL movement can be replicated as input/state at a bounded update rate, while discrete
  interactions and battle actions remain reliable ordered commands.
- No multiplayer feature is complete until two separate game instances pass join, action,
  disconnect, reconnect, and state-consistency tests.

## Initial implementation order

1. Keep the current project bootable offline.
2. Define command/event schemas and protocol version.
3. Add a local in-process session adapter to exercise the same command path.
4. Add host/client transport only after the adapter tests pass.
5. Test two real Kristal instances and document platform/network requirements.
